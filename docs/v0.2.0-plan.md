# v0.2.0 — Background call recording

## Goal

Vocora runs in the background and, whenever a phone call happens, records both sides of the
conversation into a single file, without the user having to open the app.

## Why the recorder is not the app

Both sides of a call can only be captured from `AudioRecord` with the `VOICE_CALL` audio source,
and that source is refused to ordinary apps no matter which permissions they hold. It works for the
shell user, which is why `scrcpy --no-video --audio-source=voice-call --record=call.opus` records
correctly: the scrcpy server runs as shell through ADB.

Shizuku gives the same privilege without a PC. A Shizuku `UserService` is a process the Shizuku
server starts with the shell uid, so it can open `VOICE_CALL` exactly like scrcpy does. Started with
`daemon(true)` it also keeps running after the app process is gone, which is what keeps recording
alive in the background: it is not a child of the app, Android's background limits do not apply to
it, and Doze does not freeze it.

## Components

| Component | Runs as | Responsibility |
| --- | --- | --- |
| `RecorderService` (Shizuku `UserService`) | shell | Watch call state, record, write the file |
| Vocora app | normal app uid | Settings, recording list, service status, notification |

The app may die at any time; only the UserService matters while a call is being recorded. The app
binds to it to read state and change settings.

## Storage

The user picks a folder once with `ACTION_OPEN_DOCUMENT_TREE`.

The SAF grant belongs to the app uid, so the shell process cannot write through that URI. The tree
URI is therefore resolved to a real path (`primary:Recordings/Vocora` →
`/storage/emulated/0/Recordings/Vocora`) and handed to the recorder, which writes to it directly.

- Default folder: `/storage/emulated/0/Recordings/Vocora`
- File name: `2026-10-02_14-35-12_+34600111222_incoming.m4a`
- Format: AAC in `.m4a`, via `MediaCodec` + `MediaMuxer`, mono, 64 kbps
- After closing a file, trigger a MediaStore rescan so file managers list it

Limitation accepted for this version: only the primary (internal) volume. Tree URIs on SD cards or
USB storage do not map to a usable path, so the picker is restricted to internal storage.

## Staying alive

1. `daemon(true)` on the UserService — the main mechanism.
2. A reboot stops Shizuku, and on a non-rooted device the user has to start it again by hand. Vocora
   listens for `BOOT_COMPLETED` and for the Shizuku binder, and relaunches the UserService as soon
   as Shizuku is up.
3. HyperOS kills background apps aggressively. Point 2 only works with **Autostart** enabled for
   Vocora and its battery setting on **No restrictions**. Detect this and warn on the status screen.
4. While recording, the shell service starts a foreground service in the app with
   `am start-foreground-service` (background start limits do not apply to shell), so there is a
   visible, persistent notification during the recording.

## Manifest and permissions

- `RECORD_AUDIO` — for the app's own fallback paths and so the UI can show the state honestly
- `READ_PHONE_STATE` — call state and number in the UI
- `RECEIVE_BOOT_COMPLETED` — relaunch after a reboot
- `POST_NOTIFICATIONS` — recording notification
- `FOREGROUND_SERVICE` + `FOREGROUND_SERVICE_MICROPHONE`, service declared with
  `foregroundServiceType="microphone"`

## Milestones

1. **Smoke test.** Minimal UserService that records 10 seconds of a call to a fixed path. Proves
   `VOICE_CALL` works from Shizuku the same way it works from scrcpy.
2. **Call detection** inside the service: start, end, number, incoming or outgoing.
3. **Real output**: chosen folder, file naming, AAC encoding, MediaStore rescan.
4. **Survival**: `daemon(true)`, relaunch after reboot, HyperOS checks and warnings.
5. **UI**: folder picker, recording list, service status.
6. **Notification** while recording.

## Risks and open questions

- **Main risk:** whether `AudioRecord` with `VOICE_CALL` behaves inside a Shizuku UserService the
  same as inside the scrcpy server. Same uid, so it should, but appops and the system context differ.
  Milestone 1 exists to answer this before anything is built on top of it.
- Shizuku must be running before a call arrives; after a reboot there is a window where recording
  does not work until the user starts Shizuku.
- Behaviour with VoLTE and VoIP calls (WhatsApp, Telegram) is unverified; this plan targets regular
  phone calls.
- Dual SIM and call waiting are out of scope for this version.
