# v0.6.0 — Talking to the server

## Goal

Recordings reach [vocora-server](https://github.com/IgorMy/vocora-server), come back transcribed, and
the list says where each one stands without the app having to ask the server every time it opens.

## What the server offers

| Endpoint | Use |
| --- | --- |
| `POST /recording` | mixed, uplink and downlink plus `contact`, `date`, `direction`. 201 created, 200 unchanged |
| `GET /recording?updated_since&deleted&limit&offset` | What changed, for syncing |
| `GET /recording/{id}` | Detail with `transcription` and `segments` |
| `DELETE /recording/{id}` | Soft delete |
| `GET /server/live` | Public liveness |

Two things about it shape the design:

- **A recording is identified by `{date}-{contact}-{direction}`.** Re-uploading the same content
  answers 200 and changes nothing, so **retrying an upload is safe** and the queue can be dumb.
- **`segments` carry `speaker: uplink | downlink`**, which is what recording each side apart was for:
  who said what is a fact, not a guess.

## The local database

A table of recordings, written by the app, holding what the list needs to draw itself: folder, date,
contact, direction, duration, upload state, server id and status, and the cached transcription.

Today the list is built by reading the folder and opening every file to measure it, which is why it
takes a moment on a cold start. With the table it draws immediately and the disk is only read to
reconcile.

**The recorder cannot write to it.** It runs as the shell user in another process and the database
belongs to the app, so the app is the only writer. Reconciliation on open does both directions:

- A folder on disk with no row gets one.
- A row whose folder is gone is deleted, as agreed.

## Upload

A queue that survives the app being closed, retrying with a growing delay, and that only runs when
the server URL and the token are both set.

Worth knowing: **nothing can upload while the app is dead**. Uploads happen in the app process, so a
call recorded with the app closed is queued and sent the next time something wakes it. The recorder
can wake it the same way the cancel button does, which is the one piece that has to be built rather
than configured.

## What the list shows

| State | Where it comes from |
| --- | --- |
| Not uploaded | Local, nothing sent yet |
| Uploading | Local, the queue is working on it |
| Uploaded, waiting | Server `status=pending` |
| Transcribing | Server `status=transcribing` or `embedding` |
| Done | Server `status=done` |
| Failed | Server `status=failed`, with its error |

Server states are refreshed with `GET /recording?updated_since=<last sync>`, which is what that
endpoint exists for.

## Transcription

Downloaded when a recording is opened, cached in the database, and shown under the player as a
conversation: each segment on the side of whoever said it, uplink and downlink told apart.

The sheet grows to at most half the screen, so the list stays visible behind it.

## Settings

Server URL, token, and whether the server answers. Both fields have to be filled for the queue to
run at all.

## What this needs that the project does not have

- A database and a queue that survive restarts, and an HTTP client that can post multipart.
- The recorder waking the app when a call ends, so uploads do not wait for the app to be opened.

## Decided

- **The network is a setting**, Wi-Fi only by default. Three files of a ten minute call are around
  15 MB, which is not something to send over mobile data without being asked.
- **Uploading changes nothing on the phone.** The recording stays where it is; the server takes over
  from there and the app only comes back to ask how it is going.
- **Whether the server answers from outside the house is the owner's business**, not the app's. The
  queue just tries, and a server that cannot be reached is a retry like any other.

## Open question

- **The server has no version endpoint.** `GET /server/live` only answers `{"status": "ok"}`, so
  Settings can say whether the server answers but not which version it runs. Showing the version
  means adding it there first.
